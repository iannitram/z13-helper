Scope: `main.py`, `src/`, `decky/`, `tooling/`, `install.sh`, `packaging/` on `origin/main` at `8521ffc`. Read-only: no code was changed.
Method: a read-through of the hardware-write paths (`hardware_controller`, `profiles`, `profile_control`, `fan_watchdog`, `max_fans_state`, `power_range`, `decky/main.py`, `packaging/host/`, `tooling/boondock`, `tooling/profiles/`) plus targeted searches (`sysfs` reads and writes, `subprocess` use, locks, duplicated helpers, test references) over the rest. ## Engine: `src/profiles.py`, `src/max_fans_state.py`, `src/profile_control.py`

1. **medium** `src/profiles.py:1036-1052`, `1060-1064`, `1100-1105`. `apply()` sets the shared Max Fans flag to `enabled=False` at line 1046 and only sets it back to `True` after the 100% write succeeds (line 1100-1105). A timeout after the base profile write (line 1050) or a failed `fancurve --set` (line 1100) returns with the flag still OFF. *Why:* M2 says Max Fans survives; here the user's intent is dropped without a trace in the store. The comment at 1051 says this is deliberate for the timeout case, but a plain failed fan write has no such reason. *Fix:* on any non-timeout failure restore `initial_max_fans_on` before returning; for the timeout case keep it suspended but record a `suspended` marker so the UI can show "Max Fans paused: write timed out" and the watchdog can resume it later. *Test gap:* `tests/test_profiles_max_fans.py` has 8 tests; none exercises a failed write or the cleanup path (`clear_z13ctl_default_custom_tdp` is not referenced by any test), so neither a failed `fancurve --set` nor a failed cleanup is covered.
2. **medium** `src/profiles.py:1049-1062`. `apply()` carries on to TDP, fan and lighting writes when the base profile write fails (`base_ok` False, not a timeout). *Why:* TDP and curve then land on the wrong firmware profile, and `apply_by_name` still reports the other steps as ok. *Fix:* stop after a failed base write (the exit hook has already run, so report it) or at least skip the TDP and curve steps.
3. **medium** `src/profiles.py:849-864` vs `src/hardware_controller.py:258-285` vs `decky/main.py:472-478`. Three separate builders of `z13ctl tdp --set ... --pl2 ... --pl3 ... [--force]`. `profiles.apply_tdp()` and `decky/main.py:tdp_argv()` pass the stored values through; neither checks them against `power_range.detect_ranges()` (the stored envelope is 5-93 W, the Armoury PL1 range on this kernel is 28-80 W). *Why:* a profile saved on one kernel is sent as is on another; z13ctl then rejects or clamps it and the profile apply reports an error with no hint. Boondock (findings 44 and 45) has the same problem at 20 W. *Fix:* one `profiles.tdp_argv(tdp, ranges)` used by all three; clamp and note, as `power_range.tdp_status()` already does for display.
4. **medium** `src/profiles.py:225-257` (and the same code in `src/max_fans_state.py:84-113` and `decky/main.py:267-350`). The lock helper falls back to *no lock* on any `OSError` other than `StoreLockError` (read-only directory, unusual filesystem). *Why:* silent loss of mutual exclusion between the app, the CLI and Decky; a lost update to `profiles.json` or `max-fans.json` is then possible with no log line. *Fix:* log a warning once when falling back.
5. **medium** `src/profiles.py:1198-1210`, `src/profile_control.py:80-90`. No lock spans a whole apply. `apply_by_name()` reads `active`, applies, then calls `set_active()`; the app's worker queue, a Decky `z13-profile apply`, the login restore unit and the resume hook can overlap. Only the file writes are serialised. *Why:* two applies interleave their z13ctl writes (platform profile from one, curve from the other) and `active` ends up as whichever finishes last. SPEC M6 (one owner) is the open #23 / PR #153 work; listed so it is not forgotten when that lands. *Fix:* **(#153)** one apply lock owned by the state owner.
6. **low** `src/profiles.py:658-682`. `validate()` uses `isinstance(v, int)`, and `bool` is an `int` in Python, so `undervolt: false` validates as 0 and `battery_limit: true` is rejected only because 1 is below the floor. *Fix:* `type(v) is int`. `validate()` also does not type-check `max_fans`.
7. **low** `src/profiles.py:686-706`. `validate_curve()` accepts equal temperatures ("non-decreasing") but the docstring (`profiles.py:687`, "temps increasing") and `hardware_controller.py:318` ("monotonically increasing") imply a rising curve; neither says "strict", and the `< prev_t` check is what lets equal temps through. The finding stands on the code, not on a quote. *Why:* a curve with two equal temperatures validates, saves, and then fails at apply time. *Fix:* require `t > prev_t`.
8. **low** `src/profiles.py:182`, `275`. Comments say the Decky backend "runs as root"; `AGENTS.md` and `decky/main.py` say it runs as deck. The root-safe code is still right for `install.sh` / root callers, but the comment misleads. *Fix:* reword.
9. **low** `src/profiles.py:1012-1025`, hooks. Enter and exit hooks run `bash -lc <string from profiles.json>` with a 120 s bound. The file is user-owned, so this is not a privilege problem, but any process running as the user (including Decky's backend, which edits this file) can plant a hook that runs on the next app or CLI profile switch (`profiles.py:1264` sets `skip_hooks` for `restore`, so a login restore never runs hooks). *Why:* worth knowing for the threat model; no fix needed beyond keeping `restore` hook-free as it is. Severity low.
10. **low** `src/max_fans_state.py:163-172`. `save()` writes `max-fans.json` with a bare `open(tmp, "w")` and `os.replace`, no `fsync`, a temp name keyed only by pid, and no ownership handling, whereas `profiles._atomic_write_text` and `decky/main.py:_atomic_write_text` are root-safe (`tests/test_atomic_write_root_safe.py`). A corrupt or unreadable file also makes `load()` return `None`, and the next `save(enabled=...)` then drops the saved curve snapshot. *Fix:* reuse the shared writer; treat unreadable as "unknown", not "empty".
11. **low** `src/profile_control.py:80-90`. `switch()` returns early when `name == self.active_name()`, so choosing the already-active profile never re-applies it, even after a failed apply left the hardware differing. `reapply_active()` exists but its only callers are `profile_control.py:148` (removing the active profile) and `:165` (`factory_defaults`); nothing in the tray calls it. *Fix:* none required; document it.
12. **low** `src/profile_control.py:62-70`, `src/dashboard_ui.py:580-589`. `shown_max_fans()` is called only from Qt-thread UI code (`dashboard_ui.py:532`, timer at `:853`); only the Max Fans OFF closure (`dashboard_ui.py:580-582`) reads the store on the worker thread while the Qt thread may be saving it; `load_store` is lock-free when no repair is needed, so a half-written file cannot be read (atomic replace), but a stale read is possible. Low.

## Hardware wrapper: `src/hardware_controller.py`, `src/power_range.py`, `src/epp.py`

13. **medium** `src/hardware_controller.py:271-281`. `set_tdp(pl1=None, pl2=..., pl3=...)` uses `min(provided)` as the `--set` anchor. `z13ctl tdp --set N` pins *all three* rails to N, so PL1 becomes `min(pl2, pl3)` even though the docstring says "None means leave that rail alone". *Why:* the only live callers pass all three today, so this is latent; the first caller that passes one rail (e.g. a single slider push) will change PL1 to a value nobody chose. *Fix:* require all three, or read the current values first (but never read `ppt_*`: principle 5), or reject partial calls with `ValueError`.
14. **medium** `src/hardware_controller.py:138-140`, `258-281`, `315-346`, `142-192`. The wrapper validates only undervolt (line 374) and the curve length. It does not check battery limit (40-100), TDP bounds or ordering (the Decky clamp enforces PL1 <= PL2 <= PL3, the wrapper does not), curve percent (0-100) or raw PWM (0-255), temps, or brightness level. *Why:* `HardwareController` is the module the SPEC calls the hardware seam; the safety lives in callers (`validate()`, the sliders, `clamp_tdp`). Anything new that calls it directly gets no protection. *Fix:* put the clamps in the wrapper and keep the callers' checks as the UI layer.
15. **low** `src/hardware_controller.py:120-136`. `get_platform_profile()` falls back to `"balanced"` when sysfs and `z13ctl profile --get` both fail. `rewrite_profile()` (used by every watchdog recovery) then writes `balanced`, which can change a `quiet` or `performance` machine. *Fix:* raise instead of guessing.
16. **low** `src/hardware_controller.py:168`, `183`. Timeouts are recognised by `str(e).startswith("z13ctl write timed out after ")`. The same string is matched in `profiles.py:1062`, `1085`, `1120`, `src/profile_control.py`, `decky/main.py:_extract_z13ctl_timeout`. *Why:* a reworded message silently turns a timeout (which must not be retried) into a retryable error. *Fix:* a `Z13CtlTimeout(RuntimeError)` subclass in `host.py`.
17. **low** `src/hardware_controller.py:107-118`, `src/profiles.py:927`. **Withdrawn:** the original claim (failures logged as noise on every recovery) is false. Neither `restore_undervolt()` nor `apply_undervolt` logs; `restore_undervolt` returns a message string (collected into the watchdog's recovery result) and returns `None` when the profile has no undervolt. Lines 352-380 are the undervolt getters/setters, not this path.
18. **low** `src/power_range.py:34-61` vs `64-90`. The host probe script duplicates `bounds()` and the detection rule inline (documented "keep in sync"). `tests/test_power_range.py` covers the local path; whether a test compares the two is not obvious. *Fix:* a test that execs `_HOST_PROBE` against a temp tree and compares with `_probe_sysfs_local`.
19. **low** `src/power_range.py:126`. `tdp_status()` does `int(tdp[k])` with no `KeyError`/`ValueError` handling; a hand-edited profile with a missing rail breaks `power_state()` (Decky) and the Fans window.

## Fan watchdog: `src/fan_watchdog.py`

20. **medium** `src/fan_watchdog.py:418-435`, `461`, `468`. The auto-mode stall recovery hands `_recover_auto(temp)` to the worker without re-checking state when it runs. `_recover` re-checks `_max_fans_on()` before the rewrite and again before the 100% write (lines 461 and 468) and cancels if it changed; `_recover_auto` (418-435) has no such re-check. If the user turns Max Fans ON or applies a profile between the decision and the worker run, `_recover_auto` still rewrites the platform profile and resets the curve (`fancurve --reset`), which drops a just-applied custom curve or the Max Fans pin until the next tick. *Fix:* re-read `_max_fans_on()` and `custom_fan_curve_enabled()` first and return "skipped" if they differ from the decision.
21. **low** `src/fan_watchdog.py:437-480`. `_recover()` reads the custom curve points before `rewrite_profile()` and writes them back with `set_fancurve_pwm`. If the read returns a partial or stale list (the tach and cached readback can lie, see AGENTS "Fans"), the write puts that back. The curve length is checked by the wrapper (8 points) but not that it matches the profile's. *Fix:* prefer the active profile's curve when the points differ from it.
22. **low** `src/fan_watchdog.py:614-658`. `_OwnedRotatingHandler` and `FanTrace` duplicate directory-opening and ownership code that also exists in `decky/main.py:139-236` (`_open_dir_chain`, `_write_in_dir`) and `src/app_log.py`. Candidates for one shared helper (ADR 0001 allows `py_modules` copies of `src/` files).

## Desktop UI: `src/dashboard_ui.py`, `src/fans_window.py`, `src/apply_worker.py`, `main.py`

23. **high** `src/dashboard_ui.py:688-693`. `_apply_battery_limit()` calls `controller.set_battery_limit()` and `config.set("battery_limit", value)`. It does not write the active profile's `battery_limit`. Decky's `apply_battery_limit()` (`decky/main.py:824-839`) does. `z13-profile restore` at login applies the profile's `battery_limit`, or the 80% fallback (`profiles.py:1177-1183`), so a limit chosen in the desktop app is reverted at the next login or resume restore. *Why:* M1 ("a login or resume restores the active profile") and M6 (frontends agree) are both broken for this field, and the user sees the charge limit change by itself. Firmware also resets it on reboot (AGENTS). *Fix:* save through `ProfileControl.save(profile, "battery_limit")` as the Fans window already does for other fields; drop the `config.json` copy once migrated.
24. **medium** `src/dashboard_ui.py:595-606`, `630-650`. Brightness and lighting writes also go straight to `HardwareController` and `config.json` (`config.set("brightness", ...)`), only lighting also updates the profile (`set_profile_lighting`). Same drift as #23 for brightness: `profiles.apply` step 6 re-applies the *profile's* brightness at restore. Decky's `set_brightness` stores only in plugin state (`_save_plugin_state`), a third place. *Fix:* one brightness field in the profile, as for the battery limit.
25. **medium** `src/dashboard_ui.py:959-1008`. The InputPlumber D-Bus listener is the fallback when the evdev reader cannot start. InputPlumber is masked on this machine and must not be unmasked (AGENTS). The fallback calls `SetTargetDevices` and sets `InterceptMode` to *all* (`_INTERCEPT_MODE_ALL`) with plain `subprocess.run(["dbus-send", ...])` calls, each with a 3 s timeout, on the Qt thread, bypassing `host.py`. If InputPlumber were ever running, this would intercept every controller input into the app. Effectively dead code and a latent hazard. *Fix:* delete the fallback, show "Side button: unavailable".
26. **low** `src/dashboard_ui.py:896-950`. Side-button host reader: `subprocess.run(["flatpak-spawn", "--host", "pkill", ...], timeout=5)` runs on the Qt thread at startup and at quit (up to 5 s of freeze if the host is slow). When the reader exits, the button stays dead until restart (logged; no self-heal exists and ROADMAP does not track one).
27. **low** `src/dashboard_ui.py:569-577`. `_toggle_max_fans.on()` swallows every exception while snapshotting the curve (`except Exception: pass`). A failed read means no `saved_curve` is stored and Max Fans OFF later falls back to the profile curve or firmware auto: acceptable, but nothing is logged.
28. **low** `src/dashboard_ui.py:589`. The message "Max Fans OFF — profile curve restored" is returned even when the plan was `reset_fancurve()` (firmware auto).
29. **low** `src/apply_worker.py:30-36`. The worker thread never stops and its queue is unbounded; a hung z13ctl call (bounded by the 20 s write timeout, but 120 s for hooks) blocks every later write including fan recovery. Acceptable by design, but a quit during a long apply waits on a daemon thread that is killed mid-write. Note for #153.
30. **low** `src/single_instance.py:165`. `InstanceServer._accept()` calls `conn.recv(64)` with a 1 s timeout on the Qt main thread; a client that connects and sends nothing freezes the UI for 1 s per connection. The socket sits in a private runtime directory, so only the user's own processes can do it.
31. **low** `src/dashboard_ui.py` (1018 lines) holds the window, tray, Max Fans, lighting, updates, service control and side-button code in one class; `src/fans_window.py` and `profile_control.py` split out cleanly, this one did not. Not a bug; it is why #23 will be hard to land.

## Decky backend: `decky/main.py`, `decky/src/`

32. **medium** `decky/main.py:1122-1128`. `Plugin.set_profile(profile)` runs `z13ctl profile --set <profile>` with whatever string the frontend sends, and returns z13ctl's raw output as the message. It is the direct firmware-profile path (QAM "performance profile"). *Why:* (a) no check against `quiet|balanced|performance` (z13ctl may accept `custom`); (b) it bypasses the profile engine: TDP, curve, undervolt and EPP are not re-applied, so Max Fans (if on) loses its curve until the watchdog's next recovery, and the active app profile no longer matches the hardware, contrary to M5 ("never show a state that did not apply"). *Fix:* validate against `BASES`; either route through `z13-profile` or follow with the same restore sequence as `fan_watchdog._recover`.
33. **medium** `decky/main.py:267-350`, `351-390`, `139-236`, `612-676`. Decky carries its own copies of the file lock, atomic writer, Max Fans state loader/saver, lightbar recovery and brightness-per-device loop. ADR 0001 explains why Decky cannot import `src/profiles.py` (root-owned `py_modules/` copies), but it allows `py_modules/` copies of other `src/` files, and `max_fans_state.py`, `host.py`-level lock code and `lightbar` recovery are good candidates. Drift already exists: `src/max_fans_state.py:save()` is not root-safe, Decky's is; the lightbar-reset stamp lives in the Flatpak's per-app runtime directory for the desktop app but in `/run/user/1000/` for Decky and the host CLI (`profiles._runtime_dir`, `decky/main.py:112`), so the desktop app and Game Mode can each reset within the same 120 s window. *Fix:* ship one shared `store_io.py` through `py_modules/` (add it to `PLUGIN_FILES` in `install.sh` and the `tooling/install_check.py` manifest).
34. **low** `decky/main.py:1135-1137`, `772-803`. `set_tdp` with `enabled=False` runs a full `z13-profile apply` (a 5-10 s fan dip, by design, commented). With `enabled=True` while Max Fans is ON, `tdp --set` activates z13ctl's `custom` profile, which re-applies its stored curve and can drop the Max Fans pin until the watchdog notices (the desktop `push_tdp` has the same issue). *Fix:* re-pin 100% after a TDP write when Max Fans is on.
35. **low** `decky/main.py:1155-1177`. `_unload()` cancels the tasks but never awaits them; a watchdog tick running `asyncio.to_thread(watchdog.tick)` can still be mid-write when the plugin unloads (Decky reloads the plugin on every file change; see `quiesce_loader`). The write lock is not released by cancel in the worker thread.
36. **low** `decky/main.py:48`, `66`, `src/host.py:30`. `/home/deck` is hard-coded in three places (Decky's `Z13_PROFILE`, `FAN_TRACE_DIR`, `host.DECK_HOME`). Fine for SteamOS (the SPEC supports only the `deck` user), but they will need one definition.
37. **low** `decky/src/` (TypeScript) was not audited line by line; `profileSwitch.test.ts` is not run in CI (`.github/workflows/tests.yml` runs pytest and the Decky unittest only).

## Packaging and host scripts: `packaging/host/`, `install.sh`

38. **high** `packaging/host/systemd/system/z13-fan-resume.sh:26-44`. After resume the script runs `z13-profile restore`; only when that exits 0 does it stop. `z13-profile` exits 1 when *any* step fails (`profiles._print_results`), and a wedged lightbar, the failure the project already knows best, fails the lighting step on its own. The script then falls into the fallback and writes a generic curve (`40:127,...` raw PWM, or the 100% curve when Max Fans is on), over the profile's own fan curve that restore had just applied, and without the profile's TDP. *Why:* the user's chosen curve is replaced after exactly the resume events that go wrong, and the journal line says "profile restore unavailable" although it ran. *Fix:* separate "restore did not run" (exit 127, missing file) from "restore ran with a failed step"; only fall back for the first, and re-check fan state after the second instead of writing a curve.
39. **medium** `packaging/host/systemd/system/z13-fan-resume.sh:36-43`. The last-resort fallback writes `echo 2 > .../pwm*_enable` on the `asus_custom_fan_curve` hwmon node directly, as root. SPEC's Won't list says any hardware write that does not go through `z13ctl` is out of bounds (principle 1). It is a deliberate escape hatch for a failed `fancurve --reset`, but it is not recorded as an exception in ROADMAP §2. *Fix:* record the exception in the ROADMAP or remove the sysfs write.
40. **low** `packaging/host/systemd/system/z13-fan-resume.sh:13`, `tooling/profiles/z13-max`, `z13-balanced`, `z13-cool`. Legacy curves still start at 40 °C, with no 20 °C anchor (AGENTS "Fans": low-temperature behaviour differs, built-ins start at 20 °C). The z13-* scripts are the retired path (`z13-restore-profile` execs `z13-profile restore` first), but they remain installed and still write curves without going through the profile owner.
41. **low** `packaging/host/systemd/user/z13-helper.service:3`, `z13-button-watcher.service:3`, `system/z13-lightbar-reset.service:3`, `tooling/spike1_qam_test.py:16`. `Documentation=file:///home/deck/dev/z13-helper/...` and a usage example with a home path in files that ship to the host. AGENTS rule 8 bans home paths in code. Replace with the GitHub URL.
42. **low** `packaging/host/systemd/system/z13-lightbar-reset.sh:38-55`. Writes the USB `authorized` attribute directly, not through z13ctl. It is the documented recovery (Phase 7) and guarded (one device, fixed VID:PID, polkit allows only `start` for user `deck`), so only noted. If the re-authorize fails the lightbar stays disabled and only the journal says so.
43. **low** `install.sh` (863 lines) was not read in full. What was read is careful (staged copy, byte verification, `sudo mktemp -d`). `PLUGIN_FILES` (`install.sh:83-86`) is a hand-kept list that must match `decky/main.py`'s imports and `tooling/install_check.py`; a new `py_modules` import will fail at plugin load, not at install. *Fix:* a test that parses `decky/main.py` imports and checks them against `PLUGIN_FILES` (`tests/test_install_sh.py:176` keeps its own list of `py_modules` files; whether it is compared with the imports was not checked).

## Tooling

44. **high** `tooling/boondock:103-105`, `134`. `hardware-on` snapshots `ppt_pl1_spl`, `ppt_pl2_sppt` and `ppt_fppt` with `cat`, and `status` reads `ppt_pl1_spl`. ROADMAP principle 5 and `power_range.py`'s header say reading PPT values can hard-lock the EC and must never happen. The built-in Boondock profile hooks run only `session-on`/`session-off`, but `boondock on`, `boondock hardware-on` and `boondock status` are documented user commands. *Fix:* snapshot the active profile (`z13-profile active` + its stored `tdp`) instead of live PPT values, and drop the PPT line from `status`.
45. **medium** `tooling/boondock:29`, `109`. Hard-coded 20/30/40 W. PL1 20 W is below the 28 W Armoury floor on kernel 7.2 (`power_range.ARMOURY_RANGES`); the command's output goes to `/dev/null`, so a rejection is silent and Boondock reports "TDP → 20 W". *Fix:* check the exit status; take the value from `power_range` or the profile.
46. **low** `tooling/boondock:36`, `78`. Screen brightness is written with `sudo tee` on the backlight node. The app's `screen_brightness.py` does the same write as `deck` with `tee`; the `sudo` here can prompt in a hook that has no terminal (the hook timeout is 120 s).
47. **low** `tooling/z13_fanlog.sh`, `tooling/diag/*`, `tooling/profiles/z13-cool`, `z13-max`: read-only or retired; no tests. `tooling/z13_qam.py` is a back-compat alias whose only importer is the by-hand spike `tooling/spike1_qam_test.py`; both can go when the spike is retired.
48. **low** Dead code: `src/state_events.py` and `src/post_update_state.py` are imported only by their tests (no import in `src/`, `decky/`, `main.py`, `install.sh`). `tooling/post_update/*` has no caller outside `tests/` either. SPEC M7 ("the tray and Decky say SteamOS updated: N tasks", "run the selected ones with a plan") has the building blocks but no wiring on `main`. **(#154)** is expected to add the first caller; until then M7 is not implementable from the UI. This is SPEC drift: the SPEC status line says #27 remains unfinished, which matches, but the MAP and README should not describe these modules as part of the running app.
